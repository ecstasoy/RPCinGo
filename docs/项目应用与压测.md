# RPCinGo · 项目应用与压测（面试备用）

> 目的：回答「这个项目你实际应用过吗 / 性能如何」。核心叙事——**没上生产，但按生产标准验证过、压过、定位过瓶颈、知道怎么优化**。

---

## 一、可运行示例（一套框架，两种典型形态）

| | **calculator**（`examples/calculator/`） | **microservice/user**（`examples/microservice/`） |
|---|---|---|
| 客户端模式 | **Fixed**（单连接池，固定地址） | **Discovery**（etcd 发现 + 负载均衡） |
| 编解码 | JSON，无压缩 | **Protobuf + Gzip** |
| 注册中心 | 无 | **etcd**（动态端口 `:0`，lease+KeepAlive 自动摘除） |
| 方法 | Add/Subtract/Multiply/Divide | GetUser/ListUsers |
| 拦截器 | Tracing + Recovery + Logging + Metrics | —— |
| 可观测 | Prometheus `/metrics`(:9091) + Jaeger | —— |
| 演示点 | 拦截器链 / CallTyped / 可观测性 / 压测 | 服务发现 / Protobuf+Gzip / 动态寻址 |

辅助：`examples/calculator/bench/`（自带压测工具，`-c` 并发 / `-d` 时长，输出 QPS + p50/p90/p99）、`test/e2e/rpc_e2e_test.go`（端到端测试）、各包单测 + `go test -race`。

**一句话**：用同一套框架搭了 fixed（JSON+全套治理）和 discovery（Protobuf+Gzip+etcd）两种形态，证明编解码、客户端模式、治理组件都可插拔。

## 二、压测结果（本机 loopback 实测）

环境：本机回环、单 server 进程、`-c 32 -d 30s`。

| 配置 | 平均 QPS | p50 | p90 | p99 | max | 真实错误 |
|---|---|---|---|---|---|---|
| **基线**：JSON + 全套拦截器 + 每请求日志 | **~25,100** | 964µs | 2.19ms | 6.68ms | 173ms | 0 |
| **调优**：Protobuf + 去热路径日志/Tracing | **~74,200** | 336µs | 723µs | **2.02ms** | 53ms | 0 |
| **提升** | **≈ 3.0×** | 2.9× | 3.0× | 3.3× | — | — |

> 调优版 30s 内完成 **222 万**次请求；基线 75 万次。
> （另：基线 `-c 8 -d 10s` ≈ 20,400 QPS、p99 3.0ms，可见并发从 8→32 时基线吞吐没线性涨——瓶颈不在并发度。）

**「错误」其实是 0**：两次的错误数都恰好等于并发数（8、32）——压测用 `ctx` 控时长，到点时每条 goroutine 正好有一个在飞请求被取消，是收尾的尾部取消，不是真实失败。

---

## 三、优化项 → 效果归因

调优版相对基线只做了三件事，合计带来 ~3× 吞吐：

1. **去掉每请求 `fmt.Printf` + Logging 拦截器**：基线一次压测产生了 **191 万行日志**，热路径写盘 I/O 是头号瓶颈。
2. **去掉 Tracing 拦截器**：每请求少了一次 span 分配/上下文操作（Jaeger 未运行时仍有构造开销）。
3. **JSON → Protobuf**：编码更快、体积更小。

> 长尾（基线 max 173ms、p99 6.7ms）主要来自 **GC stop-the-world + 日志 I/O 抖动 + 压测端延迟切片反复扩容**——实时 QPS 曲线能看到掉到 5k 的尖谷。调优后 max 降到 53ms、曲线平稳在 75k~83k。

**还能继续优化的方向**（没做，但能讲）：压测端用 per-goroutine 直方图（hdrhistogram）替掉全局 `latMu`、Metrics 用自定义 registry、对象池复用 buffer 降 GC。

## 四、面试话术

### 电梯版（30 秒）
> 「它没上生产，是我为吃透 RPC 原理写的。但我按生产标准验证过：搭了 fixed 和 discovery 两个示例、接了真实 etcd 和 Jaeger、跑了并发压测和 e2e 测试。本机 32 并发下基线约 2.5 万 QPS、p99 6.7ms；我定位到瓶颈是**热路径日志和 JSON 编码**，去掉后换 Protobuf 提到 **7.4 万 QPS、p99 2ms，约 3 倍**。」

### 被追问「怎么证明真跑过 / 性能怎么样」
> 报数字 → **读数字** → 定位瓶颈 → 知道下一步：
> 1. 基线 2.5w QPS、调优 7.4w QPS（loopback / 32 并发 / 零真实错误）；
> 2. 我发现吞吐没随并发线性涨，说明瓶颈不在并发度；
> 3. 归因到**每请求日志写盘（191 万行）+ Tracing span + JSON**，逐项去掉/替换拿到 3× 提升；
> 4. 长尾是 GC + 日志 I/O，下一步可上对象池 + 压测端去全局锁。

### 其它常见追问
- **「上生产还差什么？」**→ 慢调用熔断、分布式限流、etcd watcher 重连、Metrics 标签基数治理、配置层 duration 统一（都已定位到 file:line）。
- **「为什么不用 gRPC？」**→ 造轮子为吃透原理；能讲清 gRPC 用 codegen、我用反射的 trade-off。
- **「遇到最难的 bug？」**→ 帧交错→加 writer 协程串行写；部分写丢字节→`writeFull`（讲现象→定位→根因→修复）。

---

## 五、要点速记

- 没上生产 ≠ 没应用过；**「按生产标准验证 + 知道边界」** 是更强的信号。
- 错误数 = 并发数 = 尾部取消，**真实错误 0**。
- 基线 ~2.5w QPS / p99 6.7ms → 调优 ~7.4w QPS / p99 2ms，**≈3×**。
- 瓶颈不在协议层，在**热路径日志 + JSON + GC**——能定位、能优化，才是重点。

> 数据为本机 loopback 实测，非生产环境；用于说明「能定位瓶颈并优化」，不作绝对性能背书。
