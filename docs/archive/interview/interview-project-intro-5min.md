# RPCinGo 项目介绍（5 分钟面试版）

## 讲述稿

我想介绍的项目是 **RPCinGo**，这是我基于 Go 从零实现的一个基于 TCP 的 RPC 框架。这个项目的目标不是简单写一个 demo，而是把一个 RPC 框架里比较核心的能力完整做出来，包括 **自定义协议、编解码、连接复用、服务发现、负载均衡、容错限流，以及可观测性**。

我当时做这个项目，主要是想把平时在 Dubbo、gRPC 这类框架里看到的核心机制，自己真正落到代码里。因为平时用现成框架时，很多能力是“会用但不一定真的理解实现细节”的，比如为什么要有定长 Header、怎么解决 TCP 粘包拆包、请求和响应怎么在一条连接上正确配对、服务实例上下线后客户端怎么实时感知，这些我都想自己做一遍。

整个项目从架构上可以分成几层。最底层是 **Protocol 层**，我设计了一个 **20 字节定长 Header + 可变长 Body** 的二进制协议。Header 里会带协议版本、消息类型、编解码方式、压缩方式、`RequestID` 和 `BodyLength`，这样接收方就能先读固定长度 Header，再按长度读 Body，解决 TCP 的粘包拆包问题。上层是 **Codec 层**，支持 JSON 和 Protobuf 两种编解码，可以根据场景切换，JSON 调试方便，Protobuf 更适合生产环境。再往上是 **Transport 层**，底层基于 TCP 做请求发送和响应接收。

这个项目里我觉得比较有代表性的点有四个。

第一是 **连接复用和多路复用**。高并发下如果每次 RPC 都新建 TCP 连接，三次握手和内核资源开销会很明显，所以我实现了连接池来复用长连接。同时在单条 TCP 连接上，我用 `RequestID` 做请求和响应的关联，这样可以让多个请求并发复用同一条连接，服务端即使乱序返回，客户端也能通过 `pending map` 正确把响应路由回对应的调用方。

第二是 **服务发现和负载均衡**。在微服务场景下，服务实例会动态扩缩容，所以我接入了 etcd 做注册中心。服务端启动时会注册实例并持续 heartbeat，客户端会从 etcd 拉取实例列表，并通过 watch 机制实时感知实例变化。拿到实例列表后，我实现了 **轮询、加权轮询、随机、一致性哈希** 四种负载均衡策略，分别适配不同场景，比如一致性哈希更适合有缓存亲和性的服务。

第三是 **容错能力**。在真实分布式环境里，下游不稳定是常态，所以我在客户端实现了重试，在出口侧做了熔断，在入口侧做了限流。熔断我采用的是基于滑动窗口统计错误率的方式，当错误率超过阈值时直接拒绝请求，避免持续打挂下游；限流则实现了令牌桶和滑动窗口两种算法，分别适合平滑限流和硬性窗口限流的场景。

第四是 **可观测性和扩展性**。我把横切逻辑抽象成了客户端和服务端双侧的拦截器链，内置了 Recovery、Logging、Metrics、Retry 和 Tracing。这样业务逻辑和这些非功能逻辑是解耦的，像 Prometheus 指标和 OpenTelemetry Trace 都可以通过拦截器无侵入地接进去。

这个项目里我认为最关键的收获，不只是“写了一个 RPC 框架”，而是我对 RPC 的关键路径有了比较系统的理解。比如一条请求从 client 发起，到协议编码、连接发送、服务端收包、方法分发、响应返回，再到客户端按 `RequestID` 配对，这整个链路每一层为什么这样设计、有哪些性能和可靠性 trade-off，我现在都能比较清楚地讲出来。

如果用一句话总结，这个项目让我把“会使用 RPC 框架”推进到了“能自己实现一个具备核心能力的 RPC 框架”的程度。

## 面试时的简短收尾

如果面试官继续追问，我通常会往三个方向展开：

- 协议设计：为什么用 20 字节定长 Header，怎么解决粘包拆包。
- 连接模型：连接池和单连接多路复用是怎么配合工作的。
- 服务治理：etcd watch、负载均衡、熔断和限流在真实链路里分别解决什么问题。
