## Top 20 高频追问

1. 为什么要自己做一个 RPC 框架，而不是直接用 gRPC / Dubbo？
   参考回答：这个项目的目标不是替代成熟框架，而是把 RPC 最核心的链路自己做一遍，包括自定义协议、TCP 粘包拆包、多路复用、连接池、服务发现、负载均衡、熔断限流和可观测性。这样我不是停留在“会用框架”，而是能解释一条 RPC 调用为什么这么设计、每一层的 trade-off 是什么。

2. 为什么协议设计成 `20 字节定长 Header + 可变 Body`？
   参考回答：核心是让接收方先稳定读出一段固定长度的元信息，再按 `BodyLength` 精确读取包体，这样最容易解决 TCP 粘包拆包问题。Header 里带 `Magic / Version / MsgType / Codec / Compress / RequestID / BodyLength`，既能做协议校验，也能支撑运行时编解码切换和请求响应配对。

3. TCP 是字节流，你怎么解决粘包拆包？
   参考回答：我用的是“定长 Header + 长度字段”方案。接收端先 `io.ReadFull` 读满 20 字节 Header，再解析出 `BodyLength`，然后第二次 `io.ReadFull` 把 Body 按长度读满，所以不会把半包或多包解析错。

4. 为什么支持 JSON 和 Protobuf 两种编解码？默认怎么选？
   参考回答：JSON 更适合调试和演示，因为人眼可读；Protobuf 更适合生产，因为体积更小、序列化更快、类型约束更强。我的框架把 Codec 放进 Header 做运行时切换，实际建议是开发调试用 JSON，真实链路优先 Protobuf。

5. 为什么一条 TCP 连接上还能并发多个请求？怎么保证响应不会串？
   参考回答：因为我在应用层引入了 `RequestID`，客户端每发一个请求就分配一个唯一 ID，并在本地 `pending map` 里登记。服务端响应时原样带回这个 `RequestID`，客户端 `readLoop` 收到响应后按 ID 找到对应调用方唤醒，所以即使服务端乱序返回也不会串。

6. `RequestID` 在项目里具体起了什么作用？
   参考回答：它本质上是多路复用的路由键。没有它，单连接上多个并发请求的响应没法和调用方一一对应；有了它，客户端就能把网络层“异步到达的响应”重新还原成调用方看到的“同步返回结果”。

7. 为什么要做连接池？和单连接多路复用分别解决什么问题？
   参考回答：多路复用解决的是“一条连接上并发承载多个请求”，连接池解决的是“不要每次调用都重新建连”。前者提升单连接利用率，后者降低三次握手、内核资源分配和短连接抖动，两个是互补关系。

8. 连接池为什么用 `channel` 而不是 `slice + mutex`？
   参考回答：因为 `channel` 很适合表达“有限容量的空闲资源池”，`Get` 和 `Put` 都能通过 `select/default` 做非阻塞快路径。这样代码更直接，池满时能自然地选择关闭连接而不是阻塞等待，也少了一层手动条件变量管理。

9. 连接池里的连接什么时候会被判定为无效并销毁？
   参考回答：主要有三类情况：连接本身不健康、空闲时间超过 `maxIdleTime`、或者生命周期超过 `maxLifetime`。这样既能及时清理坏连接，也能避免超长生命周期连接积累半开连接、NAT 清理、状态漂移之类的问题。

10. 为什么服务发现选 `etcd` 而不是 `Consul` / `Nacos`？
    参考回答：因为这个项目更像“RPC 框架核心能力实现”，我最需要的是强一致的实例列表、基于 lease 的自动摘除，以及 watch 驱动的实时发现，这三件事 etcd 的模型最直接。像 Consul/Nacos 更偏完整服务平台能力，不是这个项目阶段的重点。

11. 客户端是怎么拿到实例列表的？为什么既要全量拉取又要 watch？
    参考回答：第一次调用某个服务时，客户端会先从 etcd 按服务名前缀全量拉实例列表，写入本地缓存；之后主要靠 watch 订阅增量变化，实时更新缓存。这样做兼顾了启动时的一致视图和运行时的低延迟更新。

12. 服务发现和负载均衡分别解决什么问题？
    参考回答：服务发现解决“现在有哪些可用实例”，负载均衡解决“这次请求具体打哪一台”。前者维护候选集，后者负责流量分配，它们是串联关系，不是替代关系。

13. 你实现的一致性哈希适合什么场景？和轮询相比有什么不同？
    参考回答：一致性哈希适合有粘性需求的场景，比如本地缓存、用户会话、分片路由。和轮询相比，它不追求每次都平均，而是追求“相同业务 key 尽量稳定命中同一实例”，并且扩缩容时只迁移少量 key。

14. 熔断和限流有什么区别？为什么两个都要做？
    参考回答：限流解决的是“流量太多”，熔断解决的是“下游太差”。前者是预防过载，后者是故障隔离；只有限流没有熔断，下游挂了还会持续打；只有熔断没有限流，突发流量还是可能把自己打满。

15. 熔断为什么用滑动窗口？为什么是按 `service` 维度而不是 `instance`？
    参考回答：滑动窗口只关注最近一段时间的健康度，比累计错误次数更能反映“当前状态”。现在先按 `service` 维度实现，是为了先把框架功能跑通，但这会有误伤问题；更理想的设计其实应该是按 `instance` 维度做 breaker。

16. 令牌桶和滑动窗口限流分别适合什么场景？
    参考回答：令牌桶适合限制平均速率，同时允许一定突发；滑动窗口适合做“最近 1 秒最多 N 次”这类更严格的窗口约束。前者更实用，后者更精确。

17. 拦截器链为什么要设计成双侧的？客户端和服务端分别适合放什么逻辑？
    参考回答：因为有些横切逻辑天然发生在调用出口，比如 Retry、TracingClient；有些逻辑天然发生在调用入口，比如 Recovery、Metrics、TracingServer。双侧拦截器能把这些非业务逻辑统一接进来，同时不污染核心调用代码。

18. Tracing、Metrics、Logging 是怎么接进调用链的？
    参考回答：它们都被抽象成拦截器，在请求真正落到 invoker 前后执行。比如 Tracing 在客户端创建 span 并注入 metadata，在服务端提取 trace context 并继续建子 span；Metrics 统计调用次数和延迟；Logging 记录请求、错误和 TraceID。

19. 这个项目里你最不满意的一点是什么？如果继续做会先改哪里？
    参考回答：我最不满意的是注册中心保活和熔断粒度这两块。当前 server heartbeat 和 etcd keepalive 有重复语义，breaker 也是按 service 粒度而不是按 instance 粒度；如果继续做，我会先把注册接口重构成 registration handle，再把 breaker 下沉到实例维度。

20. 这个项目真正上线，你最担心的风险是什么？
    参考回答：我最担心的是“实例缓存陈旧”和“故障隔离不够细”。比如 watch 线程退出后缓存可能继续使用旧实例，或者单实例故障导致整个服务被 service 级 breaker 误伤；所以真正上线前我会优先补 watch 恢复、stale cache 回源、per-instance breaker、TLS 和最大包体限制。

## 二、协议与编解码

### 高频追问

1. 为什么 Header 要做成固定长度？
   参考回答：Header 做成固定长度，是为了让接收端永远知道“先读多少字节才能拿到元信息”，这比变长头部更容易实现和排障。
2. 为什么是 `20` 字节，不是 `16` 或 `24`？
   参考回答：20 字节是字段设计后的自然结果：前 8 字节放协议元信息，后 8 字节放 `RequestID`，最后 4 字节放 `BodyLength`，再留少量保留位做扩展。
3. Header 里的每个字段分别有什么作用？
   参考回答：`Magic` 用来校验协议类型，`Version` 管协议升级，`MsgType` 区分请求和响应，`Codec`/`Compress` 决定 Body 的处理方式，`RequestID` 用于多路复用响应路由，`BodyLength` 用于帧边界解析。
4. 为什么协议里要放 `Magic Number`？
   参考回答：`Magic Number` 的意义是快速拒绝错误协议流量，比如有人把 HTTP 请求打到 RPC 端口，没有魔数的话服务端会把乱数据当 Header 解析。
5. 为什么 BodyLength 用 `uint32`，有没有上限问题？
   参考回答：`BodyLength` 用 `uint32` 是为了让头部足够紧凑，同时 4GB 的理论上限对普通 RPC 已经足够；但真实生产里我还会再加一个更小的业务级最大包体限制。
6. 为什么把编解码方式和压缩方式放到 Header 里？
   参考回答：把编解码和压缩方式放到 Header 里，接收端就可以按包做运行时选择，不要求两端靠外部配置硬编码成同一套。
7. 为什么支持 JSON 和 Protobuf 两套 Codec？
   参考回答：两套 Codec 是为了覆盖不同场景：JSON 便于调试，Protobuf 适合性能敏感场景。
8. 什么场景适合 JSON，什么场景适合 Protobuf？
   参考回答：如果是开发联调、调试看包，JSON 更方便；如果是正式链路，Protobuf 更合适，因为体积更小、序列化更快。
9. Gzip 压缩为什么不是默认无脑开启？
   参考回答：Gzip 不是无脑开启，因为压缩有 CPU 成本，小包甚至会因为压缩头和算法开销变慢；更适合大包、文本类负载。
10. 如果客户端和服务端的 Codec 配置不一致怎么办？
    参考回答：客户端和服务端的“默认配置”不一致没关系，因为最终以 Header 里的字段为准；真正要避免的是某端根本不支持某种 Codec。
11. 你怎么做协议向后兼容？
    参考回答：协议兼容主要靠 `Version` 和保留字段，旧版本读到不认识的能力时至少可以拒绝，而不是误解析。
12. 如果以后要支持鉴权、校验和、流式传输，Header 怎么扩展？
    参考回答：如果以后支持鉴权、校验和、流式分片，我会优先消耗 `Reserved`，再考虑扩展 Header 或引入扩展头，而不是直接破坏现有帧格式。

## 三、TCP、多路复用与连接池

### 高频追问

1. 为什么底层选 TCP 而不是 UDP？
   参考回答：底层选 TCP 是因为 RPC 需要可靠、有序、面向长连接的传输能力，UDP 下很多事情都得自己补。
2. TCP 已经保证有序了，为什么还要 `RequestID`？
   参考回答：TCP 保证的是字节流顺序，不保证“哪个响应对应哪个并发请求”；`RequestID` 是多路复用下请求和响应的配对键。
3. 单连接多路复用具体是怎么实现的？
   参考回答：实现方式是客户端给每个请求分配一个唯一 `RequestID`，把调用方登记到 `pending map`，然后启动 `readLoop` 持续收响应并按 ID 分发。
4. 服务端乱序返回时，客户端怎么把响应路由回正确调用方？
   参考回答：服务端即使先处理完后发回某个后来的请求，只要响应里带着原始 `RequestID`，客户端就能找到对应等待者。
5. `pending map` 的结构是什么？并发安全怎么保证？
   参考回答：`pending map` 是 `requestID -> pendingCall` 的映射，外层用互斥锁保护；每个 pendingCall 再通过 `done channel` 或错误字段通知具体调用方。
6. 为什么有了多路复用还要连接池？
   参考回答：多路复用解决的是“单连接承载能力”，连接池解决的是“不要重复建连”。高并发下如果只有单连接，多路复用再好也会受单连接瓶颈影响；如果只有连接池但每个连接只跑一个请求，又浪费了长连接潜力。
7. 连接池为什么按地址维度管理？
   参考回答：因为服务发现拿到的是一组 `ip:port` 实例，连接的真实复用单位就是 endpoint，所以池天然按地址隔离。
8. `PoolManager` 为什么要做双检锁？
   参考回答：`PoolManager` 做双检锁，是为了在读多写少场景下先走快路径，同时避免多个 goroutine 并发为同一地址重复创建连接池。
9. 连接池为什么用 `channel` 做容器？
   参考回答：`channel` 非常适合表达固定容量的空闲资源池，`Get` 和 `Put` 都能用非阻塞 `select` 快速处理，语义比 `slice + mutex` 更直接。
10. `Get` / `Put` 的快路径和慢路径分别是什么？
    参考回答：`Get` 的快路径是直接从池里取一个现成连接；慢路径是池空时新建连接。`Put` 的快路径是把健康连接放回池里；慢路径是池满或连接不健康时直接关闭。
11. 连接什么时候会被判定为过期？
    参考回答：连接不健康、空闲超时或生命周期超时，都会被判定为过期并清理。
12. 为什么既要 `maxIdleTime` 又要 `maxLifetime`？
    参考回答：`maxIdleTime` 主要是清理长期不用的空闲连接，`maxLifetime` 主要是避免一条长连接无限存活带来的半开连接、NAT 超时和状态积累问题。
13. 客户端和服务端为什么都开了 TCP keepalive？
    参考回答：因为项目以长连接和连接池为基础，空闲连接可能表面存在但实际上已经失效，TCP keepalive 能帮助更早发现这些死连接。
14. TCP keepalive 和应用层心跳有什么区别？
    参考回答：TCP keepalive 是内核层面的空闲连接探测，解决的是“连接是否还活着”；应用层心跳是业务协议层面的保活或健康语义，两者不是一回事。
15. 为什么显式关闭了 Nagle？
    参考回答：关闭 Nagle 是为了减少小包场景下的发送延迟，RPC 一般更在意时延而不是极致吞吐。

### 深挖追问

1. 多路复用和连接池配合后，吞吐和延迟分别改善在哪？
2. 单连接多路复用会不会有队头阻塞问题？

4. 如果一个连接上挂了很多 in-flight 请求，这条连接断了怎么办？

## 四、服务发现与 etcd

### 高频追问

1. 为什么选 etcd，而不是 Consul / Nacos / ZooKeeper？
   参考回答：选 etcd 是因为我最需要的是强一致的实例列表、lease 自动摘除和 watch 实时感知，这三点和 RPC 框架的注册发现闭环最匹配。
2. etcd 里的租约是什么？
   参考回答：租约本质上就是一个带 TTL 的生命令牌，key 绑定到 lease 上，只要 lease 被持续续约，key 就继续存在。
3. etcd 里的 KeepAlive 是干什么的？
   参考回答：KeepAlive 是给 lease 续命的机制，服务活着时持续续约，lease 不过期，实例 key 就不会被删除。
4. etcd 里的 Watch 是干什么的？
   参考回答：Watch 是对某个 key 或前缀的变更订阅，服务上下线时客户端不用轮询，而是等 etcd 推事件。
5. 能不能把 `租约 / KeepAlive / Watch` 串成一条完整链路？
   参考回答：完整链路是：服务启动申请 lease -> 注册实例 key 并绑定 lease -> 持续 KeepAlive -> 客户端 Watch 服务前缀 -> 如果服务挂了续约停止 -> lease 过期 -> etcd 自动删 key -> 客户端收到 DELETE 事件并更新缓存。
6. 客户端第一次怎么拿实例列表？
   参考回答：客户端第一次调用某个服务时，会先去 discovery 后端全量拉取实例列表，再写入本地缓存。
7. 为什么要本地缓存实例列表？
   参考回答：本地缓存的价值是避免每次请求都回源 etcd，降低注册中心压力，同时减少一次网络跳转。
8. 为什么有了 `GetInstances` 还要 `Watch`？
   参考回答：`GetInstances` 解决的是初始化视图，`Watch` 解决的是运行期增量更新，两个配合起来才能既拿到全量又保持实时。
9. 服务端异常退出时，实例是怎么自动下线的？
   参考回答：因为实例 key 是挂在 lease 上的，服务进程异常退出后续约停止，lease 到期时 etcd 会自动删 key，所以不依赖服务端一定能执行到注销逻辑。
10. 服务端主动注销和租约过期删除有什么区别？
    参考回答：主动注销是优雅下线，时效更快；租约过期删除是异常场景下的兜底，两者不是重复，而是正常路径和故障路径。
11. etcd KeepAlive 和 server Heartbeat 有什么不同？
    参考回答：etcd 的 KeepAlive 是 registry backend 内部针对 lease 的自动续约；server Heartbeat 是上层定时调用 `registry.Heartbeat()` 的统一抽象，对 etcd 来说它最终又会落到 `KeepAliveOnce`。
12. 你觉得现在这两套保活机制哪个更合理？
    参考回答：对 etcd 后端来说，更合理的是把保活收口到 registry backend 内部，由 lease 自己管理生命周期；server 层再单独起 Heartbeat ticker 会有重复语义。

## 五、负载均衡

### 高频追问

1. 服务发现和负载均衡分别解决什么问题？
   参考回答：服务发现给我的是候选实例集合，负载均衡负责从候选集合里挑出这一次真正要打的那台机器。
2. 你实现了哪几种负载均衡算法？
   参考回答：我实现了四种：轮询、加权轮询、随机、一致性哈希。
3. 默认策略是什么，为什么？
   参考回答：默认更适合用轮询，因为实现简单、分布均匀、没有额外业务前提。
4. 轮询、随机、加权轮询分别适合什么场景？
   参考回答：轮询适合实例能力接近的场景，随机适合高并发下低开销分配，加权轮询适合机器异构或不同实例承载能力不同的场景。
5. 一致性哈希的核心思想是什么？
   参考回答：一致性哈希的核心是把“业务 key”和“服务实例”都映射到同一个哈希环上，然后顺时针找到第一个实例节点。
6. 为什么一致性哈希要引入虚拟节点？
   参考回答：引入虚拟节点是为了让实例在哈希环上分布更均匀，避免某台机器因为物理节点少而吃到过多流量。
7. 你这里每个实例用了多少虚拟节点？为什么是这个数量？
   参考回答：当前实现里每个实例默认 150 个虚拟节点，这个值是一个工程上的折中，足够改善分布，又不会让环重建太重。
8. 一致性哈希相比普通哈希取模，扩缩容时为什么影响更小？
   参考回答：因为普通取模一旦实例数变了，几乎所有 key 都要重映射；一致性哈希只会让环上受影响区间附近的一小部分 key 迁移。
9. 这个项目里一致性哈希真正适合什么业务场景？
   参考回答：它最适合有粘性需求的服务，比如本地缓存、用户会话、分片路由。
10. 如果实例列表变化，哈希环是怎么更新的？
    参考回答：当前实现会在 `PickWithOptions` 前检查实例列表是否变化，如果变了就重建哈希环。

## 六、熔断、重试与限流

### 高频追问

1. 熔断和限流有什么区别？
   参考回答：限流解决的是“流量太大”，熔断解决的是“下游太差”，一个偏容量保护，一个偏故障隔离。
2. 为什么下游故障时“持续重试”反而会加重问题？
   参考回答：因为下游已经不健康时，持续重试只会占满线程、连接和超时预算，把故障从下游放大到上游。
3. 熔断器为什么要设计成 `Closed / Open / Half-Open` 三态？
   参考回答：`Closed` 表示正常放行，`Open` 表示快速失败，`Half-Open` 表示小流量探测恢复情况，这样既能隔离故障，也能自动恢复。
4. 你的熔断器为什么用滑动窗口，而不是简单累计错误次数？
   参考回答：滑动窗口只统计最近一段时间的健康度，比累计错误次数更符合“当前是否该熔断”的判断。
5. 熔断窗口统计了哪些指标？
   参考回答：当前窗口主要统计成功、失败和总请求数，失败率本质上是最近窗口内失败占比。
6. 失败率阈值、最小样本数、超时时间为什么这么设计？
   参考回答：阈值和样本数的目的是避免因为极小样本偶发失败就误熔断；超时时间则给下游一个恢复窗口，不让它在故障期持续受流量冲击。
7. Open 之后为什么不是永久拒绝，而是要进入 Half-Open？
   参考回答：因为熔断不是永久封禁，而是临时隔离；Half-Open 用少量探测请求判断下游是否恢复。
8. 你的熔断器是按 `service` 还是按 `instance` 粒度？
   参考回答：当前实现是按 `service` 维度，一个 service 一个 breaker。
9. 为什么现在按 `service` 粒度会有误伤问题？
   参考回答：因为 service 下可能只有某一个实例故障，但 service 级 breaker 会把整个服务都判成不健康。
10. 令牌桶和滑动窗口限流的特点和区别是什么？
    参考回答：令牌桶限制平均速率并允许突发，滑动窗口直接统计最近窗口内的请求数，语义更严格。
11. 为什么熔断这里用分桶滑窗，而限流这里用了精确时间戳滑窗？
    参考回答：熔断更关注趋势判断，允许一点分桶误差，所以用固定桶更省；限流是单次准入控制，边界精度更重要，所以时间戳滑窗更合适。
12. 令牌桶为什么允许突发流量？
    参考回答：因为桶里可以提前积攒令牌，请求高峰来时能在桶容量范围内瞬时放行。
13. 限流应该放客户端、服务端，还是两边都放？
    参考回答：两边都可以放，但目标不同：服务端限流更常用于保护入口，客户端限流更像保护调用侧资源预算。
14. Retry、Circuit Breaker、Rate Limit 三者的执行顺序是什么？
    参考回答：当前客户端默认是 Retry 作为最外层拦截器；如果配置了 RateLimit，会在 Retry 内层先做准入；Circuit Breaker 不在 interceptor 里，而是在 discovery 分支的 invoker 内部执行，所以一次重试会再次经过限流和熔断判断。

## 七、拦截器链与可观测性

### 高频追问

1. 为什么要设计拦截器链，而不是把日志、指标、重试写死在调用逻辑里？
   参考回答：拦截器链的价值是把日志、重试、限流、Tracing 这些横切逻辑从核心调用路径里抽出来，让传输逻辑和治理逻辑解耦。
2. 为什么客户端和服务端都要有拦截器？
   参考回答：因为客户端和服务端承担的职责不同，客户端更像调用出口，服务端更像调用入口，适合挂载的逻辑也不同。
3. 拦截器链为什么常被称为“洋葱模型”？
   参考回答：因为请求进入时一层层包进去，请求返回时再一层层退出来，执行形态很像洋葱。
4. 链是怎么组装起来的？
   参考回答：当前实现是从后往前遍历拦截器，把 `invoker` 一层层包起来，最终得到一个组合后的 invoker。
5. 为什么这里闭包写法要注意变量捕获问题？
   参考回答：因为闭包捕获的是变量而不是值，如果直接在循环里引用外层变量，很容易让所有闭包最终都指向最后一轮的变量值。
6. `Retry`、`Logging`、`Tracing` 分别适合放在哪一侧？
   参考回答：Retry 更适合客户端，Tracing 两侧都适合，Logging 两侧都适合但关注点不同。
7. Recovery 为什么更适合服务端？
   参考回答：Recovery 更适合服务端，因为 panic 往往发生在请求处理逻辑里，服务端需要兜底避免一个请求把整个进程打挂。
8. Metrics 为什么通常放在服务端更有意义？
   参考回答：Metrics 放服务端更有意义，因为服务端更接近真实处理入口，能稳定记录服务级 QPS、错误数和延迟。
9. Tracing 是怎么在客户端注入、服务端提取的？
   参考回答：客户端会创建 span 并把 trace context 注入到 request metadata，服务端收到后从 metadata 提取 context，再创建服务端 span 接续链路。
10. Prometheus 指标你主要采了哪些？
    参考回答：当前 Prometheus 主要采两类：按 `service / method / status` 统计的总调用数，以及按 `service / method` 统计的延迟直方图。

## 九、系统设计与 Trade-off

### 高频追问

1. 你做这个项目时，最重要的几个 trade-off 是什么？
   参考回答：我做过几个明确取舍：先优先核心链路完整性，再追求生产级完备性；先做自定义 TCP 协议理解底层原理，再考虑兼容更多生态；先做静态策略和通用能力，再做更细粒度的动态治理。
2. 为什么先做 TCP 自定义协议，而不是直接基于 HTTP/2 封装？
   参考回答：因为这个项目目标就是自己实现协议层和传输层，如果一开始就站在 HTTP/2 上，很多底层细节会被框架屏蔽掉。
3. 为什么注册中心选 etcd，而不是把注册发现完全内置？
   参考回答：因为注册发现是分布式系统通用能力，外部注册中心更符合职责分离；我的框架只需要围绕 lease/watch 和本地缓存把调用链打通。
4. 为什么先做同步 RPC，再做 MQ、异步通信之类的扩展？
   参考回答：因为项目主目标是 RPC 框架，MQ 属于更高一层的异步通信模式，不应该在第一阶段分散焦点。
5. 这个项目里你最满意的设计是什么？最不满意的设计是什么？
   参考回答：我最满意的是“协议、多路复用、连接池、服务发现”这条主链路能自洽跑通；最不满意的是“etcd 保活语义重复”和“一致性哈希的业务 key 透传还不够完整”。

### 深挖追问

1. 如果让你把这个项目改成生产可用，优先级最高的三件事是什么？
2. 如果要支持流式 RPC，你会改哪些层？
3. 如果要支持 TLS，你会放在哪一层处理？
4. 如果要支持鉴权、限流、黑白名单，哪些适合拦截器做，哪些适合协议层做？
5. 如果要支持多机房、跨地域部署，注册发现和负载均衡要怎么调整？

### 风险追问

1. 现在这个项目最大的单点是什么？
2. 如果 etcd 故障了，系统整体退化行为是什么？
3. 如果客户端缓存过期但 watch 又失效，流量会不会继续打到死节点？

## 十、压轴类问题

这些问题不一定每次都问，但一旦被问，通常是为了判断你到底有没有真正做过。

1. 这个项目里有哪个设计你后来觉得其实做错了？
2. 如果删掉一个功能，你最愿意删哪个？为什么？
3. 你实现的一致性哈希在当前调用链里真的完全生效了吗？
4. 现在的熔断器为什么说“能工作，但不够理想”？
5. 如果面试官只允许你贴着代码讲 10 分钟，你会选哪三个文件？
6. 如果要给这个项目补一组最有价值的压测指标，你会测什么？
7. 如果要给这个项目补一组故障注入实验，你会怎么做？
8. 这个项目最像哪个成熟框架的哪部分设计？
9. 你从这个项目里学到的，不是八股而是真正工程上的东西是什么？
10. 如果现在重新做一版，你会保留哪些设计，推翻哪些设计？

### 压轴题参考回答方向

1. 我会主动承认两个不够理想的点：一是 server heartbeat 和 etcd keepalive 语义重复，二是 breaker 现在按 service 而不是按 instance。
2. 如果必须删一个，我最愿意先删滑动窗口限流，保留令牌桶，因为令牌桶在工程落地上更常用。
3. 一致性哈希算法本身已经实现，但要真正做到“同一用户稳定落同一实例”，还需要在客户端调用链里显式透传稳定业务 key；这一点我会主动说明。
4. 现在的熔断器能工作，是因为它已经有三态状态机和滑动窗口；说它不够理想，是因为粒度太粗，且错误分类还不够精细。
5. 如果贴代码讲 10 分钟，我会选协议编解码、TCP client 多路复用、etcd discovery/watch 这三块，因为最能体现技术含量。
6. 我会重点测 QPS、P99 延迟、连接复用命中率、pending 请求数、实例切换后的恢复时间。
7. 我会做三类故障注入：实例突然宕机、etcd 短暂不可用、网络超时与半开连接，验证 watch、breaker 和连接池清理是否符合预期。
8. 这个项目在思想上最像简化版的 gRPC 传输链路加一部分 Dubbo 风格的服务治理能力，但实现更偏教学和原理验证。
9. 我最大的收获不是背概念，而是知道这些概念为什么会出现在工程里，比如 `RequestID`、lease/watch、Half-Open、channel pool 都是在解决具体问题。
10. 如果重做一版，我会保留自定义协议、拦截器链、连接池这几块；会重构注册接口、细化 breaker 粒度、补足最大包体限制和 watch 恢复机制。

## 最后建议

如果时间有限，优先准备这三条主线：

1. `协议 + TCP + RequestID + 连接池`
2. `etcd 服务发现 + Watch + 负载均衡`
3. `熔断 + 限流 + Retry + 拦截器链`

如果面试官继续深挖，尽量不要只背定义，要回到项目里讲：

1. 这个问题在项目里为什么会出现
2. 你当前怎么解决
3. 当前实现还有什么边界
